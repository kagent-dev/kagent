# The Giant Swarm kagent line

This repository is the kagent the [Giant Swarm Agent Platform](https://github.com/giantswarm/agent-platform)
runs: upstream [kagent-dev/kagent](https://github.com/kagent-dev/kagent) `main` at a pinned commit, plus the
patches the platform cannot run without until they are merged upstream. Team Bumblebee owns it. The line
exists because the platform moved to the kagent API v2 (`kagent.dev/v1alpha3`, Substrate actors) before
upstream has released it; the day upstream ships a release that contains every carried patch, the platform
switches to that release and this line ends.

This repository is public, and so is this file: a row's context and evidence columns name no installation,
customer, agent of an installation, management cluster or employee, and give no date of a production
incident. An environment appears by its role (a production installation, a test installation), a customer by
none. Upstream and public Giant Swarm issues and pull requests are linked; no private repository or issue is:
a row writes out what broke, in which code path, and why the change is carried.

## Which kagent are we running

The carried commits sit on top of the pin, in the order `git log --oneline main..giantswarm` shows them; their
SHAs change at every re-pin, and the ledger records the SHAs of each rebase. Each carried change is one file
under [`fork/carried/`](fork/carried): a YAML front-matter, the only part a machine reads, and a body for
people with the title, `## Change`, `## Reason` and `## History`. Two pull requests that each add one never
touch the same line, so they merge in either order. `scripts/fork/carried.sh` prints the ledger as one table
in stack order (subjects, change, upstream outcome and exit); `scripts/fork/carried.sh --check`, the
`fork-ledger` check on every pull request and push, verifies that every file names at least one subject, that
every subject it names is a commit on top of the pin and that no commit is recorded twice.

The header is the ledger's single source: `id` (the file name), `fork` (`kagent`), `theme` (one of the shared
theme slugs, `session-lifecycle` to `never-filed`), `category` (`pin`, `infra`, `bugfix`, `feature`,
`gs-specific`, `compat` or `test`), `status` (`carried`, `dropped` or `superseded`), `commits` (the carried
commits by exact subject, the pull request number GitHub appends left out: a re-pin rewrites every SHA and
keeps every subject), `upstream.outcome` (`merged`, `open`, `declined`, `superseded`, `to-file`, `fork-only`,
`drops-at-repin` or `none`), `upstream.refs` (every upstream and fork item as `owner/repo#N`),
`upstream.exit` (what makes the change leave the fork), `depends_on` (carried files of this or another line,
`owner/repo:<slug>` for another line, or an `owner/repo#N` item) and `verified` (the date the upstream state
was last checked). `## History` keeps what the file said about its upstream state before the header, verbatim;
it is prose, not state. `scripts/fork/ledger-header.sh kagent fork/carried` checks every header and runs in
the `fork-ledger` check next to `carried.sh --check` (the same rules as `fork-ledger validate`), and
`scripts/fork/ledger-header.sh --complete kagent fork/carried` checks the other direction: every commit on top
of the pin whose subject no prefix in [`fork/EXEMPT`](fork/EXEMPT) covers (the ledger's own edits, the pins,
the bots' commits, the fixups a re-pin folds) is named by exactly one file. A fix that follows a carried change
adds its subject to that change's `commits`. Proposal and vocabulary: giantswarm/kagent-upstream#719.

Rules for the ledger: a carried pull request adds its file in its `docs(fork):` commit, named after the change
(`<scope>-<the subject's first words>.md`), the subjects spelled as the commits carry them (the pull request
number GitHub appends to a subject does not count); every non-`ci(fork)` file has an upstream pull request or
a "to file" that names what the upstream filing waits on; a file leaves when the sync drops the commit because
upstream merged it (the re-pin report names the upstream commit) — delete it in a follow-up pull request, the
check is red until then. Giant Swarm-specific wiring (Substrate settings, the platform `Harness` objects,
pgvector, registries) lives in the agent-platform charts, not here.

## What is published

`.circleci/config.yml` (the fork's own, hand-written — upstream has no CircleCI pipeline) publishes on every push to the
consumed branch `giantswarm` and on the line's release tags `vX.Y.Z` and `vX.Y.Z-rc.N`, through the architect orb's
stock jobs: one `build-image` job per image and architecture (amd64 and arm64, each native on a machine of its
architecture, pushed by digest) and one `push-to-registries` job per image, which joins the two into the tagged index,
signs and attests it. A branch job whose commit already carries a release tag of the line ends green before its
checkout and builds nothing: the tag's own pipeline publishes that version, and both pipelines post the same status
contexts on the commit, which `devctl release promote` reads. Every other branch of the line — a pull request branch, a `sync/**` re-pin candidate — runs the
same eight builds with `push: false` and publishes nothing; the mirrored upstream refs (`main`, `release/v*.x`,
upstream's tags) run nothing:

Only what the platform consumes is published: the Python ADK and the CLI image are not offered on the platform
and are not built here. A dev build is the test artifact of the consumed branch — a merged
pull request or a landed re-pin — proven in agentlab on the meta chart's dev channel before the tag that consumers
depend on; a pull request's branch is proven with a build of its checkout swapped into the lab (the pipeline builds
it, pushes nothing). Its consumers: the agent-platform meta chart's dev line (`components.kagent` follows the channel;
its `kagent.tag` and the two `Harness` image digests are pinned there and re-pinned per build), agentlab, and the
test cluster following the channel. A release (below) is what the meta chart's release line resolves.

Publishing does not wait for the tests. Nothing reaches the consumed branch untested — a pull request needs a
green `ci-ok` and `scan-ok` on an up-to-date branch, and the sync lands a candidate only after both passed on
its exact head (the same commits it then force-pushes) — so the push-triggered run on the consumed branch is a
repetition; a red one is a flake to re-run or an environment drift to fix, visible on the commit and in the
Actions tab, never a reason to pull a build that was green on the same tree.

### Release scheme

A release of the line is a tag `vX.Y.Z` on the consumed branch — its own stable semver, decoupled from upstream's
version, as the RFCs prescribe for every Giant Swarm package of upstream software (giantswarm/rfc
`semantic-versioning-of-upstream-software`, `semver-based-automatic-upgrades`): the version says nothing about the
upstream version, which is documented instead — the pin in the table above and the ledger, the annotation
`io.giantswarm.upstream.version` on every image, the release's row below. `1.0.0` is the first release of the scheme,
the next major above the coupled `0.11.0-gs.N` releases it replaces, so every consumer range moves forward and none
back; a patch or a minor of the line is a patch or a minor of the version, whatever upstream did in the re-pin between;
a major is the line's own breaking change (a chart value renamed, a CRD contract changed), never upstream's numbering.
A release candidate is `vX.Y.Z-rc.N`. The pipeline publishes a tag the way it publishes a dev build — the version is
the tag without `v`; the workflow's tag filter admits `vX.Y.Z` and `vX.Y.Z-rc.N` and nothing else: the six images and
both charts under `gsoci.azurecr.io/giantswarm/kagent` at `X.Y.Z`, the digests as a row of `builds.md`. The release's
row in the table below is written by hand; `scripts/fork/ledger-check.sh` keeps it from trailing (below).

Why this shape:

- **Order.** Releases sort as plain semver, so a consumer follows the line with a range — the meta chart's release
  line `>=1.0.0 <2.0.0` — and re-resolves on every reconcile. Dev builds (`-r588f3d76t…`; before 2026-09-24 `-dev.…`) and release candidates (`-rc.N`) are
  pre-releases, which Flux's semver (Masterminds) never matches against a range without a pre-release bound; the dev
  channel is selected by `semverFilter` (above) next to a `-0` range, and nothing else.
- **No collision with the mirror.** Upstream's tags are `vX.Y.Z` too, and the mirror copies every upstream tag the
  fork lacks; a name both use would make the two refs disagree. The line's tags therefore live in a major above
  upstream's — `1.x` against upstream's `0.x` — and `scripts/fork/mirror.sh` refuses, naming the tag, to mirror an
  upstream tag whose name the fork already holds at another commit, instead of skipping it silently. The rule: when
  upstream's version approaches the line's major (upstream tags `0.99.x`, or a `1.0.0-rc`), the line moves to its next
  major first — a deliberate `v2.0.0` — and the consumers' ranges with it. Upstream's version resolvers in `ci.yaml`
  see the fork's tags too: `scripts/upgrade-from-version.sh` (the `adjacent` leg) is skipped on a non-release base such
  as `giantswarm`, and `scripts/prev-stable-version.sh` only looks at the release line below the one being built
  (`release/v0.10.x` today), where no fork tag lives.
- **Out of the wrapper's range.** Every 3.x installation of the platform selects the 0.10 wrapper chart `kagent` at
  `oci://gsoci.azurecr.io/charts/giantswarm/kagent` with `>=0.2.0 <1.0.0` and re-resolves it on every reconcile.
  The line's chart must never be resolvable there. It is not: it lives on another OCI path
  (`gsoci.azurecr.io/giantswarm/kagent/helm`) — the wrapper's repository and the line's never share a version — and
  its versions are `>=1.0.0`, outside that range besides.
- **gsoci, from CircleCI, under the line's own path.** The org publishes to `gsoci.azurecr.io` from CircleCI only —
  the architect orb's multi-arch builds, signed with cosign keyless under the project's CircleCI identity — and
  never from a GitHub Actions job: no Actions workflow of this repository holds a registry credential, and nothing
  pushes to ghcr.io. `.circleci/config.yml` is that pipeline. The repositories keep upstream's names under the
  line's prefix (`giantswarm/kagent/<image>`, `giantswarm/kagent/helm/<chart>`) — not `charts/giantswarm/kagent`,
  the wrapper chart's repository (above), and not the app catalog, which lists apps, not the component a meta chart
  pins. A consumer names the registry (`kagent.registry: gsoci.azurecr.io`) and the chart repository
  (`oci://gsoci.azurecr.io/giantswarm/kagent/helm`); the version scheme is the same for both.

A tag is cut only after the build of the same commit — its dev build on the consumed branch — has passed the
platform's proofs in agentlab on the meta chart's dev channel; the tag re-publishes the same tree under the release
version. Cut it deliberately (no tag ruleset gates it; anyone with write access can push a tag):

```bash
git tag -a v1.0.0 -m v1.0.0 <sha> && git push origin v1.0.0
# or, without a checkout:
gh api -X POST repos/giantswarm/kagent-upstream/git/refs -f ref=refs/tags/v1.0.0 -f sha=<sha>
```

Then add the row below from the run summary (or `builds.md`).

A stable release is also refused while an earlier stable release (from `1.6.0` on) has no row in the Releases table: `scripts/fork/ledger-check.sh releases` is part of the line's stable gate (below). The publish writes the row: on a stable tag the `record` job, once the release's builds.md row is on the `ledger` branch, runs `scripts/fork/releases-row-pr.sh`, which writes the row from that builds.md row, the tags and the tag's Makefile (`scripts/fork/releases-row.sh`) and opens it as the pull request `docs(fork): the Releases table carries X.Y.Z` against `giantswarm` (a `docs` commit cuts no candidate). The gate counts a row on `giantswarm` even when the promoted candidate was cut before it merged, and a row still waiting in that pull request (its branch `fork-ledger/releases-X.Y.Z`), so the next promotion never waits for its merge; a refusal links the pull request. Merge it to put the row on `giantswarm`; a closed one has its branch deleted with it. `scripts/fork/releases-row.sh X.Y.Z` writes a missing row by hand the same way. A change of the Substrate pin is held to its rows the same way: `scripts/fork/ledger-check.sh pin`, a step of the `fork-ledger` check on every pull request and push, is red unless the "Substrate version the pin runs with" row opens with the Makefile's `SUBSTRATE_VERSION` and the "Substrate the pin runs with" row names the `go/go.mod` replace target's version. Put those rows in the pull request that moves the pin, and type it `fix` or `feat` so it cuts a candidate.

A stable release runs on a stable Substrate. `check-substrate-pin`, the first job of the publish workflow and what
every image build requires, runs `make substrate-pin-check` with the tag: a `vX.Y.Z` tag whose chart pin (the
Makefile's `SUBSTRATE_VERSION`) or module pin (the `go/go.mod` replace target) carries a prerelease suffix fails
there, naming the version, and nothing of the release is published — the Substrate release is promoted first, the
pin moved to it and a new candidate cut. A candidate or a dev build passes: a candidate exists to prove a prerelease
Substrate. Every release's notes name the Substrate release it requires: the `record` job appends a "Requires"
section — the chart dependency and worker image at `SUBSTRATE_VERSION`, the module pin — to the GitHub release
once the artifacts are published, below the notes the Auto Release workflow wrote from the commits.

Both refusals are the line's stable gate, `.github/release-gate.custom.sh <version>`, and it runs before the tag. The
Auto Release workflow's stable promotion runs it on the candidate's checkout with the version about to be tagged,
after the version is decided and before the tag and the GitHub release are created: a refusal fails the run and cuts
neither, so the line never carries a stable release that looks published with nothing built. Fix the cause on the
branch, let it cut the next candidate and promote that. `check-substrate-pin` runs the same script with the tag it
publishes, the second guard for a tag pushed by hand.

## CI and security

`ci.yaml` (upstream's suite: Go unit tests and lint, Helm unit tests, protobuf contract check, manifests check,
UI typecheck/lint/unit/browser tests, Python tests and lint, multi-arch image builds, the e2e against kind +
Substrate, the upgrade legs) and `image-scan.yaml` (Trivy on every published image at CRITICAL/HIGH,
`govulncheck` over the Go module graph) run on every push to `giantswarm` and `sync/**`, on every pull
request to `giantswarm`, and — the scan — weekly. Fork differences from upstream's files: the triggers,
GitHub-hosted runners with a `docker/setup-buildx-action` builder instead of Blacksmith runners and their
builder, Docker Hub images pulled through `mirror.gcr.io` (the hosted runners' shared IPs exhaust Docker Hub's
unauthenticated pull limit), the image matrices trimmed to the published set, no `paths-ignore` (a docs-only pull request must still
report the required checks), and one aggregate job per workflow — `ci-ok`, `scan-ok` — which the ruleset requires.

`ci.yaml`'s fork-only `released-schema-upgrade` job guards the released schemas: `scripts/fork/released-migrations.sh`
exports the migrations of every release a database may have been created by (each distinct migration set of the line's
stable `vX.Y.Z` tags; up to `X.Y.*` for a pull request to `release-X.Y`), and `TestUpgradesEveryReleasedSchema` creates a
database with each, migrates it with the tree's migrations and compares its catalog (columns, constraints with names
and definitions, indexes, views) with a fresh install's; the failure names the differing objects. It runs on the sync
candidates too, so a re-pin that edits a released migration in place does not land until it carries the migration that
brings released databases along. A deliberate difference goes into the test's `allowedReleasedExtras` with its reason
(today `agent_instance_checkpoint.source_name`, which `000002` keeps for the 1.0 controller). Without the variable
`KAGENT_RELEASED_MIGRATIONS` the test skips, so `go-unit-tests` is unchanged.

Security findings are handled by the team's policy: a fixable finding is fixed (a dependency bump is a patch
like any other — upstream pull request first, carried here until merged; an image fix goes into the Dockerfile
the same way, as the two `apk upgrade` commits above). A finding upstream cannot fix yet, or a scanner
false positive, gets a time-boxed, justified ignore — `.trivyignore` with Trivy's native `exp:YYYY-MM-DD` and a
comment naming the module and the reason — so the line keeps moving; it is re-reviewed at the expiry. `govulncheck`
has no ignore file of its own, so `scripts/fork/govulncheck.sh` applies `.govulncheck-ignore` (`GO-… until=… # why`)
the same way: an expired entry fails the scan until it is re-reviewed, and only a finding with no fixed version
may be listed there.

Upstream automation the fork does not need is off: Dependabot version updates are disabled on this fork (a
fork's default; dependency updates arrive through the re-pin), Renovate runs only its regex managers for the
GitHub CLI pin in `go/github-cli.version`, the GitLab CLI pin in `go/gitlab-cli.version` and the Claude Code, Codex and omp pins of the harness images (the `ARG` lines of `go/harness/claude/Dockerfile`, `go/harness/codex/Dockerfile` and `go/harness/omp/Dockerfile`, the single source of the pinned versions, with the `Pinned*Version` constant each harness checks the binary against; Renovate moves the tags, the `Harness CLI pins` workflow (`harness-pins.yaml`) commits the per-architecture checksums of `scripts/fork/harness-pins.sh update` to Renovate's branch as the `heraldbot` App, and the `fork-ledger` check fails until they agree), and keeps its Dependency Dashboard issue as the record of the scan
(`renovate.json`, the name Renovate reads to admit a fork, with `forkProcessing: "enabled"`), `stalebot`, `conventional-label` and
`label-pull-requests` are disabled workflows (repository setting, not a file edit), `migration-immutability`
only fires on pull requests to `main`/`release/**`, which do not exist here. Upstream's workflow files do start
when the mirror is pushed (the push has to be made as the App — see "The mirror"); the sync cancels those runs
within seconds, so a cancelled run per mirrored branch or tag in the Actions tab is expected, not a failure.

## Re-pin

The line is rebased onto upstream `main` weekly (Monday 05:00 UTC) by `.github/workflows/sync-upstream.yaml`,
also on demand (`gh workflow run sync-upstream.yaml`, inputs `upstream_ref`, `dry_run`). One run:

1. fast-forwards the mirror — `main`, the `release/v*.x` branches, the tags — to upstream (`scripts/fork/mirror.sh`;
   refuses if a mirrored branch was edited; never moves or deletes a ref) and cancels the runs upstream's own
   workflow files start at the mirrored refs (`scripts/fork/mirror-quiet.sh`);
2. rebases the carried commits onto the upstream head into a candidate branch `sync/upstream-<date>-<sha7>`
   (`scripts/fork/repin.sh`; commits upstream merged in the meantime are dropped and named in the report,
   with the upstream commit they landed as; an `amend!` or `fixup!` commit is folded into the carried commit it
   names — the way a carried commit's diff or message is corrected between re-pins) and checks every hunk the carried commits brought
   (`scripts/fork/hunks.py`): one whose added lines the consumed head has and the candidate lacks, or whose
   removed lines are back, is lost — the run stops and its summary names the commit, the file and the hunk.
   A hunk upstream merged in another form, or one a re-pin reworks onto upstream's changes, is named in
   the dispatch input `accept_hunks` (a hunk id as the report prints it, or a commit for all its hunks), and
   the report lists it as accepted;
3. pushes the candidate (as the org's `heraldbot` GitHub App, whose token the run mints — a push by an App
   triggers workflows, a push with the workflow's own token would not); `ci.yaml` and `image-scan.yaml` run on it;
   the workflow waits for `ci-ok` and `scan-ok`;
4. green: force-pushes the candidate onto `giantswarm` (`--force-with-lease` on the head it started
   from), deletes the candidate, appends the row to `re-pins.md`; the pipeline publishes the dev build and
   appends its row to `builds.md`;
5. a conflict or a red check: nothing is pushed to the consumed branch; a pull request against
   `giantswarm` names the conflicting carried commit (with the files) or the failed checks, and the
   candidate branch stays for the fix. Finish by hand, then close that pull request — never merge it (a merge
   would keep the old base).
6. the pin annotation `index:io.giantswarm.upstream.version=main@<sha7>` in `.circleci/config.yml` names the
   upstream pin on every published image ("What is published") and the sync does not edit it: after a landed re-pin,
   a pull request against `giantswarm` moves it to the new pin (its own commit — a pull request cannot fix up the
   `ci(fork)` carried commit; a manual re-pin may fold it). `record` compares the stamped annotation with
   `git merge-base` on every build: a dev build whose annotation lags warns, a release whose annotation disagrees is
   refused before its ledger row.

A re-pin is proven before anything depends on it: the agent-platform dev line re-pins the new build's tag and
`Harness` digests, and agentlab on the dev channel runs its proofs from the published artifacts.

### Manual re-pin

The same steps by hand, for when the workflow is broken or a conflict needs a human:

```bash
git clone https://github.com/giantswarm/kagent-upstream && cd kagent-upstream
git remote add upstream https://github.com/kagent-dev/kagent.git
CANDIDATE=sync/upstream-$(date -u +%Y%m%d)-manual scripts/fork/repin.sh   # exit 2 = conflict, report in repin-report.md
# on a conflict: git rebase --autosquash --onto upstream/main "$(git merge-base origin/giantswarm upstream/main)" ; fix ; git rebase --continue
sed -i "s|upstream.version=main@[0-9a-f]*|upstream.version=main@$(git merge-base HEAD upstream/main | cut -c1-7)|" .circleci/config.yml && git commit -qsam 'chore(fork): upstream pin annotation'   # the pin annotation moves with the pin (step 6); fold it into the ci(fork) commit if you rebase interactively
git push origin "$CANDIDATE"                      # ci.yaml + image-scan.yaml run on sync/** ; wait for ci-ok and scan-ok
gh workflow run sync-upstream.yaml --repo giantswarm/kagent-upstream --ref giantswarm \
  -f candidate="$CANDIDATE" -f upstream_ref="$(git merge-base HEAD upstream/main)"
```

The dispatch lands the candidate the way the weekly sync lands its own: `scripts/fork/take-candidate.sh`
refuses a candidate that is not a `sync/**` branch, does not sit on `upstream_ref`, still contains the consumed
head (a merge, not a rebase), lost a carried hunk `accept_hunks` does not name (`scripts/fork/hunks.py`, as in
step 2 — run it before the push: `scripts/fork/hunks.py "$(git merge-base origin/giantswarm upstream/main)"
origin/giantswarm HEAD`) or whose ledger `scripts/fork/carried.sh --check` rejects; the workflow then waits
for `ci-ok` and `scan-ok` on its head, force-pushes it onto `giantswarm` with a lease on the head it read,
deletes the branch, fast-forwards the mirror and appends the `re-pins.md` row. Nobody needs a bypass of the
consumed branch's ruleset, and nobody force-pushes by hand.

### The mirror

`main`, the `release/v*.x` branches and the tags are fast-forwarded by the sync as the App (`scripts/fork/mirror.sh`;
`protect-mirror-main` ruleset on `main`: no deletion, no force-push). The workflow's own token cannot be used:
GitHub refuses any push that creates or updates a file under `.github/workflows` without the `workflows`
permission, mirrored upstream commits included, and `GITHUB_TOKEN` never has it. An App push starts upstream's
workflow files at the mirrored refs; `scripts/fork/mirror-quiet.sh` cancels them right after. Upstream's CI
resolves the upgrade-test baseline from the fork's own release branches and tags, so the mirror must carry them
(the fork's own release tags `vX.Y.Z` share upstream's shape and live in a major above upstream's — "Release scheme"; `mirror.sh` refuses to mirror an upstream tag whose name the fork already holds at another commit, so a collision stops the sync, naming the tag, instead of one side silently winning).
If a mirrored branch was ever edited, the sync refuses to fast-forward it; restore it with
`git push --force-with-lease=refs/heads/<branch> origin upstream/<branch>:<branch>` after lifting the ruleset
briefly, then run the sync again. `gh workflow run sync-upstream.yaml -f mirror_only=true` mirrors without
re-pinning.

## Branch protection

Ruleset `protect-consumed-branch` on the default branch: no deletion, no force-push, changes only through a
pull request with one approval, required status checks `ci-ok` and `scan-ok` on an up-to-date branch. Pull
requests are **rebase-merged, never squashed**: every commit on the consumed branch is one carried patch with
its own upstream exit, and the re-pin drops a commit only when its patch matches an upstream commit — a squash
would weld a cherry-picked upstream fix to unrelated changes and lose that.
Bypass: the `heraldbot` GitHub App (the org's automation App, installed on every repository; the sync
pushes with a token it mints from the org secrets) always — that is the re-pin's force-push; repository
administrators for pull requests only (merging an own green pull request without waiting for the approval).
Ruleset `protect-mirror-main` on `main`: no deletion, no force-push. Teams `team-bumblebee` and `bots` have
write access.

## Before you carry a patch

A carried patch needs a placement and an upstream exit, and its `fork/carried/` file records both: the
placement in `## Reason` and `upstream.outcome`, the exit in `upstream.exit`. Place it by the first class
that holds: drop (nothing consumes it), upstream already has it (name the mechanism and its configuration),
platform (a Giant Swarm product choice, in the agent-platform charts or our own images), upstream issue (a
generic gap that needs design), upstream pull request (a small generic fix), fork-only (a named reason and a
dated exit). Before a new field, flag or schema, look for an upstream mechanism or an established standard
first. The full rule is Team Bumblebee's *Upstream placement* section, kept in its internal plans
repository.

## Contributing

- **Every patch is prepared for upstream; a human decides what goes upstream.** Work on
  a branch of this repository (`fix/…`, `feat/…`) and open the pull request here against `giantswarm`: the
  change is one upstream-ready commit, with its `fork/carried/` file. Beside it, push its upstream branch
  `upstream/<slug>` to this repository: the commit on the mirror's `main` at the pin (or on the upstream
  branch it depends on), DCO-signed, with no fork references, its message the upstream pull request's
  text, and hand it to the maintainers' upstream review. The carried file's `Upstream` column records it:
  "to file — prepared in the fork: branch `upstream/<slug>`", with what the branch is based on and the upstream
  search. Opening the upstream pull request (kagent-dev/kagent) is not a step of the fork pull request: a human
  decides what goes upstream and opens it, and an agent never opens, comments on, reviews or closes anything on the
  upstream repository. Once one is opened, the `Upstream` column links it and the upstream pull request names the
  fork commit, so the two reference each other.
- **The ledger cites public sources only.** This repository is public: `FORK.md` and `fork/` link no issue,
  pull request or file of a private repository, and a reason that lives in one is written out in a sentence
  instead. The `public-links` job of `fork-ledger.yaml` fails a pull request that adds such a citation
  (`scripts/fork/public-links.sh --added <base>`; without arguments it checks every citation).
- **Lint with `make -C go lint`** (`make -C go lint-fix` to apply the fixes), the command CI's `go-lint`
  runs. `go/.golangci.yaml` enables `kubeapilinter`, a custom linter loaded as a Go plugin from
  `go/bin/kube-api-linter.so`; a plugin loads only into a binary built with the same toolchain and
  dependencies, so a stock `golangci-lint` stops with `unable to load custom analyzer kubeapilinter:
  plugin: not implemented`. The target builds the plugin and a matching `golangci-lint` from source into
  `go/bin/` on its first run and needs only Go and git; never strip the linter from a copy of the
  config to lint with a stock binary.
- **A carried commit takes a type that releases.** Pull requests here are rebase-merged, so each commit's
  own subject reaches the Auto Release workflow, and its `cliff.toml` skips `test`, `docs` and `style`: a
  push that carries only those cuts no release candidate, and the change has no published artifact to be
  proven from. A carried commit whose change is a test or documentation is therefore typed
  `chore(<scope>):` (`chore(e2e): …`), on `giantswarm` and on a maintenance branch alike; every other type
  (`feat`, `fix`, `refactor`, `perf`, `chore`, `build`, `ci`, `security`) cuts the next `-rc.N`. The
  upstream pull request keeps the title upstream expects (`test(e2e): …`). The `fork/carried/` file commits
  stay `docs(fork):`: the ledger is no change to prove, and it ships with the next candidate.
- **Queued changes are a stack of commits; every pull request keeps the base `giantswarm`.** `ci.yaml`
  runs on pull requests to `main`, `release/**` and `giantswarm` only, so one based on another pull
  request's branch gets the CircleCI image validations and nothing else: no `go-unit-tests`, no `go-lint`,
  no `ui-tests`, no `test-e2e`, and no `ci-ok` — 8 checks where the same branch against `giantswarm` runs
  41 (2026-09-26, #112). A change that depends on a queued one therefore branches from the head of the pull
  request below it and is opened against `giantswarm`: the diff shows the commits below until they land,
  and the suite runs on the code that will land. Each pull request carries its own commit and its
  `fork/carried/` file, one ledger row per carried commit.
  - **Merge the top of the stack once, with `--rebase`.** Its branch contains every commit below, so the
    one merge lands the whole stack, each commit on its own, and the one CI run on the top's head is the
    run that counts.
  - **Close each lower pull request as carried**, with one line naming the merge (`Carried by #<n>,
    merged as <sha>`), never merged: its commits are already on `giantswarm`.
  - **No replacement pull request per base move.** The ruleset requires an up-to-date branch, so every
    merge to `giantswarm` outdates the open pull requests. Only the top of the stack is merged, so only it
    has to be up to date: the lower pull requests are never merged, never refreshed and never re-filed,
    and a queue of three costs one CI run, on the top's head. A top that falls behind before it merges is
    replaced once, by a pull request from a fresh branch of `giantswarm` with the stack's commits on it in
    order; the base is never merged into a branch, which a rebase merge would drop and so hide a conflict
    until it lands.
  - **Never a force push on the line**, not with a lease: the ruleset forbids it on `giantswarm`, and on a
    branch it rewrites the commits a review and a green run were given for, so what merges is no longer
    what ran. A branch that is behind is replaced, as above.
- **A personal fork** is for exploration that may never be proposed; the moment a change is meant for the
  platform it moves here.
- **A patch lives here until upstream merges it**; the next re-pin drops it. A patch upstream rejects is
  either re-proposed in the shape the maintainers want or recorded in its `fork/carried/` file as a
  deliberate permanent difference with the reason — the target is none.
- **A re-pin force-pushes `giantswarm` and strands the open pull requests built on it.** The commit yours
  branched from leaves the branch's history, so GitHub recomputes the merge base as the old upstream pin:
  the diff grows to the whole carried stack and the pull request turns `DIRTY` (156 files, +54k lines,
  2026-09-25, #93 and #112). Check yours after a re-pin with
  `gh pr view <n> --json changedFiles,mergeStateStatus`. Recover without a force push: branch from the new
  `origin/giantswarm`, cherry-pick your commits (the `fork/carried/` file is yours alone, nothing conflicts),
  then open a replacement and close the stale one naming it. An upstream pull request is unaffected:
  its base, the mirror, only fast-forwards.
- Anything Giant Swarm-specific (Substrate wiring, platform `Harness` objects, registries, security contexts)
  belongs to the agent-platform charts, not to this line.
- Never commit to `main` (the mirror), `sync/**` or `ledger`.
